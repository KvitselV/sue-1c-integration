# Методика расчёта рентабельности торговой точки

Реализация: `src/sue/domain/profitability.py`. Каждая величина ниже снабжена меткой
происхождения, которая доходит до интерфейса и до ответов API
([ADR 0004](adr/0004-explicit-data-provenance.md)).

## Исходные данные

| Величина | Источник | Метка |
|----------|----------|-------|
| Сумма реализации | Σ `amount` по документам `sale` | `accounting` |
| Сумма возвратов | Σ `amount` по документам `return` | `accounting` |
| Себестоимость из учёта | Σ `costAmount` там, где поле передано | `accounting` |
| Доля себестоимости категории | `data/fixtures/modeled/cost_markup_by_category.json` | параметр модели |
| Доля накладных расходов | `SUE_OVERHEAD_RATE`, по умолчанию 12% | параметр модели |

Строки возвратов хранятся с отрицательным знаком, поэтому все суммы получаются
обычным суммированием без особых случаев в запросах.

## Формулы

```text
gross_revenue     = Σ amount по документам реализации                        [accounting]
returns           = Σ amount по документам возврата                          [accounting]
revenue           = gross_revenue − returns                                  [accounting]

cost_accounting   = Σ costAmount, где поле передано                          [accounting]
cost_modeled      = Σ (amount × cost_ratio(category)) для строк без costAmount [modeled]
cost              = cost_accounting + cost_modeled          [accounting | modeled | accounting+modeled]

gross_profit      = revenue − cost                                           [derived]
gross_margin_pct  = gross_profit / revenue × 100                             [derived]

overhead          = revenue × overhead_rate                                  [modeled]
operating_profit  = gross_profit − overhead                                  [derived]
operating_margin_pct = operating_profit / revenue × 100                      [derived]
```

Метка себестоимости определяется полнотой выгрузки: `accounting`, если `costAmount`
передан во всех строках; `modeled`, если ни в одной; `accounting+modeled` в смешанном
случае. В последнем случае выводятся доли `cost_accounting_share_pct`
и `cost_modeled_share_pct` (в сумме 100%) и число строк без себестоимости.

## Точность вычислений

Суммы хранятся целым числом копеек и агрегируются средствами СУБД одним запросом
`GROUP BY store_id, category`; деление выполняется в `Decimal` с округлением
`ROUND_HALF_UP` до двух знаков. Поэтому итог по всем точкам равен сумме итогов по
каждой, а сверка с исходными файлами даёт ровно ноль расхождения
([ADR 0002](adr/0002-integer-minor-units-for-money.md)).

При нулевой выручке за период проценты не считаются: возвращается 0.00, а не ошибка
деления. Если за период нет ни одной строки, показатели не выдаются — API отвечает
`404` с кодом `no_data`, а не нулями, которые выглядели бы как результат.

## Разрез по категориям

`GET /api/profitability/{store_id}/categories` даёт выручку, себестоимость, валовую
прибыль и маржу по товарным категориям. Категория берётся из справочника номенклатуры
и используется дважды: как аналитический разрез и как основа для моделирования
себестоимости строк без `costAmount`.

## Анализ чувствительности

Доля накладных расходов — единственное существенное допущение, влияющее на
операционную прибыль. Чтобы влияние было измеримым, а не скрытым, ставку можно
сдвинуть:

```bash
curl "http://localhost:8000/api/profitability/1?sensitivity_delta=0.03"
```

Параметр принимает значения от −0.5 до 0.5 и сдвигает **только** накладные расходы;
выручка и себестоимость не меняются. На странице торговой точки строится график
чувствительности операционной маржи. Монотонность зависимости (рост доли накладных
снижает маржу) проверяется тестом.

## Почему накладные расходы моделируются

В выгрузке розничного контура 1С:Розница нет аллокации аренды, фонда оплаты труда
и общехозяйственных расходов на торговые точки: их распределение выполняется
в бухгалтерском или управленческом контуре по правилам, принятым на предприятии.
Поэтому величина задаётся как модель с явной меткой `modeled` и параметром
в настройках, а не выдаётся за учётный факт. При появлении фактических данных
об аллокации параметр заменяется, а формулы остаются теми же.

## Почему часть себестоимости моделируется

Поле `costAmount` в контракте необязательно: регистр «Себестоимость товаров»
рассчитывается по закрытию периода и на момент выгрузки может быть заполнен не для
всех строк. Вместо того чтобы отбрасывать такие строки (выручка была бы неполной)
или считать их себестоимость нулевой (прибыль была бы завышена), она моделируется
по доле категории, а доля моделируемой части выводится рядом с показателем.

## Проверка методики

Расчёт на наборе из нескольких строк с заранее известными числами совпадает
с ручным до копейки; отдельные тесты закрывают каждый вариант происхождения
себестоимости, влияние периода, нулевую выручку, отсутствие данных и монотонность
чувствительности. Подробно: [`testing.md`](testing.md).
