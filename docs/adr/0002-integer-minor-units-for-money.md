# 0002. Хранение денег целым числом копеек

Статус: принято  
Дата: 2026-08-11

## Контекст

Заявленный результат работы — сверка контрольных сумм между источником и приёмником
с нулевым расхождением. Это требование к точности, а не к оформлению: если суммы
расходятся на копейки, доказать корректность интеграции нельзя.

В первой версии все суммы хранились как `float`. При суммировании десятков тысяч
строк ошибка представления накапливается: `0.1 + 0.2 != 0.3` в двоичной арифметике.
Отдельная проблема — SQLite: тип `NUMERIC` там не является отдельным типом хранения,
и значения деградируют до `REAL`. То есть одна и та же выгрузка на SQLite и PostgreSQL
давала бы разные итоги, и «работает на SQLite» ничего не доказывало бы.

## Решение

Разделены представление в предметной логике и формат хранения.

1. В базе денежные величины хранятся **целым числом копеек** (`revenue_kopecks`,
   `cost_accounting_kopecks`), количества — целым числом тысячных долей единицы
   (`quantity_milli`). Тип — `BigInteger`: он одинаково ведёт себя на SQLite
   и PostgreSQL, поэтому суммирование можно выполнять средствами СУБД.
2. Все преобразования собраны в единственном модуле `sue.money`. Округление —
   `ROUND_HALF_UP`, как принято в бухгалтерских расчётах, и выполняется в одной точке.
3. В предметной логике используется `Decimal`; наружу (API, шаблоны, отчёты) значения
   отдаются с фиксированной точностью: два знака для сумм, три для количеств.
4. Значения из JSON преобразуются через `Decimal(str(value))`: строковое представление
   float даёт кратчайшую запись и убирает шум вида `0.30000000000000004`.
5. Расхождение при сверке считается **в минимальных единицах**, а не в округлённых
   рублях: `diff_minor_units` равен нулю только при точном совпадении.

## Рассмотренные альтернативы

**`Numeric(14, 2)` в моделях.** Естественный выбор для PostgreSQL, но на SQLite
не даёт гарантии точности, а SQLite нужен для запуска без внешних зависимостей.
Пришлось бы иметь два разных поведения в зависимости от СУБД.

**`float` с округлением в момент вывода.** Скрывает проблему, а не решает: ошибка
уже накоплена внутри агрегации, и итог по всем точкам не совпадёт с суммой итогов
по каждой.

**`Decimal` в моделях с хранением в виде строки.** Точно, но делает невозможным
суммирование средствами СУБД: пришлось бы вычитывать все строки в приложение,
что противоречит решению о переносе агрегации в `GROUP BY`.

## Последствия

Положительные: сверка «источник ↔ база» даёт ровно ноль расхождения; результат
побитово одинаков на SQLite и PostgreSQL, что подтверждается отдельным тестом,
сравнивающим показатели одного и того же пакета на двух СУБД; агрегация выполняется
одним запросом без потери точности.

Отрицательные: значения в базе нельзя читать «глазами» без деления на 100; появился
слой преобразований, обязательный к использованию — прямое обращение к полям в обход
`sue.money` считается ошибкой;
при переходе к валютам с иным числом знаков после запятой потребуется параметризовать
масштаб.

Проверяется: 20 тестов в `tests/unit/test_money.py` (округление на границах, отсутствие
накопления ошибки, отказ на нечисловых значениях) и сверка контрольных сумм на всех
сценариях данных.
