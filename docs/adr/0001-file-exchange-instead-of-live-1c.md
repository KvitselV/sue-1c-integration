# 0001. Файловый обмен вместо подключения к живой базе 1С

Статус: принято  
Дата: 2026-08-11

## Контекст

Тема работы предполагает интеграцию данных из 1С:Предприятие в систему управления
эффективностью. Доступа к рабочей информационной базе 1С:Розница в рамках работы нет:
такие базы содержат коммерческие данные предприятия, и доступ к ним не предоставляется
для учебных задач. Развернуть собственную базу 1С также не удалось — требуется лицензия
на платформу и конфигурацию.

При этом заявлять реализованным то, чего нет, недопустимо: расхождение текста работы
и кода — самостоятельный дефект.

## Решение

Механизм интеграции реализуется как **файловый обмен по формализованному контракту**,
структурно совместимому с объектами 1С:Розница:

1. Контракт описан JSON Schema (`schemas/1c_retail_exchange.schema.json`) с версией
   в `meta.contractVersion`. Состав объектов и полей соответствует справочникам
   «Магазины», «Номенклатура» и документам «Отчёт о розничных продажах», «Возврат
   товаров от покупателя» (сопоставление — в [`docs/mapping.md`](../mapping.md),
   разбор объектов — в [`docs/1c-objects.md`](../1c-objects.md)).
2. Источник данных скрыт за интерфейсом `OneCSource`. Реализация `FileExchangeSource`
   читает пакеты из каталога, `UploadedFileSource` — из загруженного файла.
3. Класс `ODataSource` объявлен как точка расширения и **осознанно не реализован**:
   его метод выбрасывает `NotImplementedError` с объяснением причины. Это честнее
   заглушки, имитирующей работу.
4. Ограничение зафиксировано в README и в этой записи.

Ключевое следствие проектирования: ETL, расчёт показателей и интерфейс не знают,
откуда пришли данные. Появление доступа к базе требует одной новой реализации
`OneCSource` и не затрагивает остальной код.

## Рассмотренные альтернативы

**Подключение к живой базе через REST/OData.** Предпочтительный вариант, недоступен
по внешней причине. Интерфейс под него сохранён.

**Прямое чтение таблиц СУБД 1С.** Технически возможно, но противоречит модели данных
платформы: физические имена таблиц и полей не документированы, зависят от версии
конфигурации и меняются при обновлении. Такое решение было бы неработоспособным
на практике, а не только недоступным.

**COM-соединение с платформой.** Требует установленной 1С и лицензии, привязано
к Windows. Не решает проблему отсутствия доступа.

**Выгрузка в CSV.** Проще в разработке, но не передаёт иерархию «документ → строки»,
не имеет схемы для валидации и не позволяет версионировать контракт. Для проверки
целостности пришлось бы придумывать соглашения поверх формата.

## Последствия

Положительные: контракт проверяем автоматически (JSON Schema плюс бизнес-правила);
сверка контрольных сумм «источник ↔ приёмник» даёт ровно ноль расхождения и является
доказуемым результатом; повторная загрузка идемпотентна по `source_ref`; отсутствие
зависимости от лицензий делает работу воспроизводимой на любой машине.

Отрицательные: не проверено поведение на реальных объёмах и реальных аномалиях
учётных данных; не решены вопросы аутентификации в 1С, прав доступа и регламентного
задания на стороне источника. Обмен файловый, то есть пакетный, а не потоковый.

Смягчение: генератор данных воспроизводит краевые случаи (отсутствие себестоимости,
короткая история точки, возвраты, пропущенные недели) и объёмный набор на 130 тыс.
строк; набор некорректных пакетов проверяет реакцию на нарушения контракта.
