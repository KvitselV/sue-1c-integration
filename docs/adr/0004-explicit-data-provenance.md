# 0004. Явное происхождение каждого показателя

Статус: принято  
Дата: 2026-08-11

## Контекст

Учётная выгрузка 1С:Розница содержит выручку и — не всегда — себестоимость строки.
Накладных расходов торговой точки в ней нет вовсе: их распределение выполняется
за пределами розничного контура. Значит, операционную рентабельность невозможно
получить только из учётных данных: часть входных величин приходится моделировать.

Это создаёт риск, который и был отмечен как замечание к первой версии: показатели,
основанные на допущениях, выглядят в отчёте так же, как учётные данные, и читатель
не может отличить измеренное от предположенного. Молчаливое смешивание источников
обесценивает весь расчёт.

## Решение

Источник значения — часть самого значения, а не примечание к отчёту.

1. Тип `ProvenanceValue` (`sue.domain.provenance`) содержит величину, метку источника,
   единицу измерения и пояснение методики. Показатель без источника создать нельзя:
   недопустимая метка приводит к исключению.
2. Метки: `accounting` — из учётной выгрузки; `modeled` — смоделировано по параметру;
   `derived` — получено расчётом из показателей выше;
   `accounting+modeled` — смешанный случай.
3. Для смешанной себестоимости дополнительно выводятся доли: `cost_accounting_share_pct`
   и `cost_modeled_share_pct` (в сумме 100%), а также число строк без `costAmount`.
   Видно не только «частично смоделировано», но и насколько.
4. Пояснение методики хранится вместе со значением и доходит до интерфейса, например:
   «Аллокация накладных расходов: выручка × 12.00%», «Себестоимость: 1498 строк из учёта
   (costAmount), 398 строк смоделировано по доле категории».
5. Метка отображается рядом с числом в интерфейсе и присутствует в ответах API,
   поэтому потребитель данных получает её автоматически.
6. Параметры моделирования (доля накладных расходов, доли себестоимости по категориям)
   вынесены в настройки и в таблицу `model_params` — они не «зашиты» в код и могут
   быть заменены согласованными с предприятием значениями.

## Рассмотренные альтернативы

**Оговорка в тексте работы.** Не защищает от неверного прочтения таблицы: читатель
видит числа, а не сноску, и потребители API не получают её вовсе.

**Считать только то, что есть в учёте (валовую прибыль).** Формально безупречно,
но исключает операционную рентабельность — то есть основную цель работы. Тема
предполагает управленческий показатель, а не пересказ учётных данных.

**Отдельный столбец «источник» в таблице отчёта.** Работает для одной таблицы,
но не переносится на API, графики и выгрузку CSV. Привязка метки к значению
решает задачу на всех путях сразу.

**Хранить метки в отдельной таблице.** Усложняет модель без выигрыша: происхождение
определяется методикой расчёта, а не хранится как данные.

## Последствия

Положительные: любой показатель отчёта прослеживается до источника; анализ
чувствительности (`sensitivity_delta`) показывает влияние моделируемой ставки
накладных на итог, что делает допущение измеримым; происхождение значения видно
в самом интерфейсе; точка с полной себестоимостью и точка без
неё визуально различимы.

Отрицательные: ответы API объёмнее, чем при простых числах; каждый новый показатель
обязан объявить источник — это дополнительное требование к разработке.

Проверяется тестами: у каждого значения есть источник и непустое пояснение;
выручка — всегда `accounting`, накладные — всегда `modeled`, производные — `derived`;
точка без `costAmount` даёт `modeled`, с полным `costAmount` — `accounting`,
смешанная — `accounting+modeled` с долями, дающими в сумме 100%.
