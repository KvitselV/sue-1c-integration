# Эксплуатация

Документ описывает развёртывание, регламентные операции и разбор сбоев.
Всё, что здесь написано, воспроизводится на чистой машине.

## Требования

| Компонент | Версия | Зачем |
|-----------|--------|-------|
| Python | 3.11 или новее | приложение (проверяется на 3.12) |
| SQLite | входит в состав Python | вариант по умолчанию, ничего ставить не нужно |
| PostgreSQL | 14 или новее | промышленный вариант |
| Docker и Docker Compose | 24 или новее | развёртывание в контейнерах |

## Развёртывание

### Локально на SQLite

```powershell
.\tasks.ps1 install
.\tasks.ps1 migrate      # alembic upgrade head
.\tasks.ps1 seed         # генерация фикстур + загрузка штатным ETL + сверка
.\tasks.ps1 run
```

Файл базы — `data/sue.db`. Включены режим WAL и контроль внешних ключей.

### Локально на PostgreSQL

```bash
docker run -d --name sue-pg -p 5432:5432 \
    -e POSTGRES_USER=sue -e POSTGRES_PASSWORD=sue -e POSTGRES_DB=sue postgres:16-alpine

export SUE_DATABASE_URL="postgresql+psycopg2://sue:sue@localhost:5432/sue"
alembic upgrade head
python scripts/seed.py
uvicorn sue.main:app --host 0.0.0.0 --port 8000
```

### В контейнерах

```bash
docker compose up --build -d
docker compose exec api alembic upgrade head
docker compose exec api python scripts/seed.py      # только для демонстрации
docker compose ps                                    # состояние healthcheck
```

Особенности сборки, важные для эксплуатации:

- образ собирается в два этапа, инструменты компиляции в финальный слой не попадают;
- приложение работает от непривилегированного пользователя `app` (uid 10001);
- `.dockerignore` исключает `.venv`, `data/*.db`, `.env` и кэши — образ не раздувается
  и не содержит настроек окружения;
- `HEALTHCHECK` опрашивает `/api/health/ready`, то есть проверяет и доступность БД;
- `CMD` применяет миграции и запускает сервер, но **не** наполняет базу: демонстрационные
  данные загружаются отдельной осознанной командой;
- при `SUE_APP_ENV=production` приложение не создаёт схему само и не стартует,
  если миграции не применены; документация OpenAPI (`/docs`) отключена;
- ответы несут заголовки `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`
  и `X-Request-Id` (можно задать своим значением);
- контур ближе к промышленному: `docker compose -f docker-compose.yml -f docker-compose.prod.yml up`.

## Настройка

Все параметры — переменные окружения с префиксом `SUE_` либо файл `.env`
(шаблон — `.env.example`). Полная таблица в [README](../README.md#переменные-окружения).
Некорректное значение приводит к отказу при старте с понятным сообщением.

Рекомендации для промышленного контура:

| Параметр | Значение | Причина |
|----------|----------|---------|
| `SUE_APP_ENV` | `production` | отключает отладочные удобства |
| `SUE_DATABASE_URL` | строка PostgreSQL | SQLite не рассчитан на конкурентную запись |
| `SUE_LOG_JSON` | `true` | журнал разбирается системой сбора логов |
| `SUE_ALLOW_LOCAL_PATH_IMPORT` | `false` | приём данных только загрузкой файла |
| `SUE_MAX_UPLOAD_BYTES` | по фактическому размеру выгрузки | защита от исчерпания памяти |
| `SUE_API_KEY` | случайная строка не короче 32 символов | загрузка данных только по ключу |
| `SUE_MARGIN_TARGET_PCT`, `SUE_MARGIN_WARN_PCT` | по регламенту финансовой службы | пороги оценки рентабельности |

## Миграции схемы

Схема изменяется **только** миграциями Alembic; `create_all` используется в тестах.

```bash
alembic current                  # текущая ревизия
alembic history                  # список ревизий
alembic upgrade head             # применить всё
alembic downgrade -1             # откатить одну ревизию
alembic check                    # модели и миграции совпадают?
```

После изменения моделей:

```bash
alembic revision --autogenerate -m "краткое описание"
alembic upgrade head
alembic check                    # ожидается «No new upgrade operations detected»
```

`alembic check` выполняется в CI на стадии `lint`: забытая ревизия останавливает
сборку, а не обнаруживается на развёртывании.

Порядок обновления версии приложения: снять резервную копию → применить миграции →
перезапустить приложение. Обратный порядок недопустим: новый код рассчитывает
на новую схему.

## Регламентный обмен данными

Штатный путь приёма выгрузки — загрузка файла:

```bash
curl -X POST http://localhost:8000/api/etl/upload \
     -F "file=@exchange_2026-06-01.json"
```

Перед реальной загрузкой полезен проверочный прогон: он валидирует пакет и считает
итоги, ничего не сохраняя.

```bash
curl -X POST "http://localhost:8000/api/etl/upload?dry_run=true" \
     -F "file=@exchange_2026-06-01.json"
```

Загрузка идемпотентна: повторная передача того же пакета не создаёт дублей —
ключом служит `source_ref` объекта (аналог GUID ссылки 1С). Поэтому повтор после
обрыва связи безопасен.

После загрузки имеет смысл сверить контрольные суммы:

```bash
curl "http://localhost:8000/api/reconciliation?path=accounting"
```

`matched: true` означает совпадение до копейки: расхождение считается в минимальных
единицах (копейках и тысячных долях), а не в округлённых рублях.

### Обмен по расписанию

Загрузка и сверка выполняются одной командой, пригодной для планировщика задач:

```bash
python -m sue.jobs.exchange --path accounting
```

Задание загружает все пакеты каталога, сверяет контрольные суммы источника и СУЭ,
сохраняет отчёт в `SUE_REPORTS_DIR` (по умолчанию `data/reports/exchange-<дата>.json`)
и завершается кодом возврата, по которому планировщик отличает успех от сбоя:

| Код | Значение | Что делать |
|-----|----------|-----------|
| `0` | пакеты загружены, контрольные суммы совпали | ничего |
| `1` | хотя бы один пакет отклонён | разобрать ошибки прогона (`/api/etl/runs`) |
| `2` | пакеты загружены, но сверка расходится | см. «Показатели не сходятся с источником» |
| `3` | обмен не начался: путь не найден или недопустим | проверить путь и `SUE_FIXTURES_DIR` |

Ключи `--dry-run` (проверить, ничего не сохраняя) и `--no-reconcile` (без сверки)
соответствуют тем же режимам, что и у загрузки через интерфейс. Отчёт содержит итоги
по каждому пакету и результат сверки, поэтому разбор сбоя не требует доступа к приложению.

Пример постановки в планировщик Windows (ежедневно в 3:10):

```powershell
$action = New-ScheduledTaskAction -Execute ".\.venv\Scripts\python.exe" `
    -Argument "-m sue.jobs.exchange --path accounting" -WorkingDirectory $PWD
Register-ScheduledTask -TaskName "СУЭ: обмен с 1С" -Action $action `
    -Trigger (New-ScheduledTaskTrigger -Daily -At 03:10)
```

## Наблюдение за работой

| Что смотреть | Где |
|--------------|-----|
| Готовность к обслуживанию | `GET /api/health/ready` (503 при недоступной БД) |
| Живость процесса | `GET /api/health/live` |
| Версия приложения и контракта | `GET /api/version` |
| Журнал загрузок | `GET /api/etl/runs`, страница `/ui/etl` |
| Ошибки конкретной загрузки | `GET /api/etl/runs/{id}/errors` |

Журнал приложения пишется в stdout. При `SUE_LOG_JSON=true` каждая запись — объект
JSON; у HTTP-запросов есть `request_id`, который возвращается клиенту в заголовке
`X-Request-Id`, поэтому жалобу пользователя можно связать с записями журнала.
У каждого прогона ETL журналируются идентификатор, счётчики и длительность.

Полезные запросы к журналу:

```bash
# Прогоны, завершившиеся сбоем
curl "http://localhost:8000/api/etl/runs?status=failed"

# Прогоны, зависшие в статусе «запущен» (штатно не должно быть ни одного)
curl "http://localhost:8000/api/etl/runs?status=started"
```

## Резервное копирование

### SQLite

```bash
sqlite3 data/sue.db ".backup 'backup/sue-$(date +%F).db'"
```

Копирование файла обычным `cp` при работающем приложении небезопасно из-за режима
WAL — используйте `.backup`.

### PostgreSQL

```bash
docker compose exec -T db pg_dump -U sue -Fc sue > backup/sue-$(date +%F).dump
docker compose exec -T db pg_restore -U sue -d sue --clean < backup/sue-2026-06-01.dump
```

Отдельно стоит сохранять каталог пакетов обмена (`SUE_FIXTURES_DIR`): содержимое базы
полностью восстанавливается из него повторной загрузкой, так что это фактически
резервная копия источника.

## Разбор сбоев

### Прогон завершился со статусом `failed`

1. Открыть ошибки прогона: `GET /api/etl/runs/{id}/errors` или страницу `/ui/etl`.
2. Определить этап (`stage`):
   - `validate_schema` — пакет не соответствует контракту. Исправляется на стороне
     выгрузки; проверить `meta.contractVersion` (принимается только `2.0`).
   - `validate_rules` — нарушено бизнес-правило: ссылка на отсутствующий магазин или
     номенклатуру, неположительная сумма, `quantity = 0` при `amount > 0`, дублирующийся
     `ref`, точность сверх двух знаков в сумме. В `location` указан адрес внутри документа.
   - `load` — сбой при сохранении (недоступна БД, нарушено ограничение целостности).
   - `audit` — не удалось записать сам журнал; смотреть журнал приложения.
3. Данные при сбое **не изменяются**: загрузка транзакционна. Достаточно устранить
   причину и повторить загрузку — идемпотентность гарантирует отсутствие дублей.
4. `severity: warning` не отклоняет запись: пакет принимается, замечание остаётся
   в журнале (например, себестоимость, втрое превышающая сумму строки).

### Прогон остался в статусе `started`

Штатно такого не бывает: при исключении существующая запись помечается как `failed`.
Статус `started` у завершённого прогона означает, что процесс был убит принудительно
(например, `docker kill`). Данные при этом не зафиксированы; повторите загрузку,
а запись оставьте в журнале как след инцидента.

### Показатели не сходятся с источником

Запросить `GET /api/reconciliation?path=<пакет>`. Поле `diff_minor_units` показывает,
где именно расхождение: разница в `documents` или `lines` означает, что часть файлов
не загружена — сравните `exchange_id` в журнале со списком файлов. Ненулевая разница
в `revenue_kopecks` при совпадающем числе строк означает, что загружена другая версия
выгрузки: сравните `source_hash` прогона с хеш-суммой файла.

### БД недоступна

`/api/health/ready` отдаёт `503` и `status: degraded`, а `/api/health/live` продолжает
отвечать `200`. Проверить: доступность узла БД, значение `SUE_DATABASE_URL`,
применённость миграций (`alembic current`). Аналитические страницы без БД работать
не могут — приложение честно сообщает о неготовности, а не показывает нули.

### Медленная работа на большом объёме

Проверить, что применены индексы `(store_id, sale_date)` и `(store_id, doc_date)`
(создаются миграцией `0001`). Расчёт показателей выполняется одной агрегацией
`GROUP BY`, ETL вставляет данные порциями
(`SUE_ETL_CHUNK_SIZE`). Для проверки поведения на объёме есть сценарий генерации:

```bash
python -m sue.datagen --out data/fixtures --scenario large --no-invalid
```

## Контроль доступа

Загрузка данных закрывается общим ключом:

```bash
export SUE_API_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
curl -X POST http://localhost:8000/api/etl/upload \
     -H "X-API-Key: $SUE_API_KEY" -F "file=@exchange_2026-06-01.json"
```

Без ключа те же запросы получают `401` и код `unauthorized`. `SUE_PROTECT_READ=true`
распространяет требование на операции чтения. Пробы `/api/health*` и `/api/version`
остаются открытыми: иначе оркестратор посчитает исправный сервис недоступным.

Ключ передаётся только через окружение или файл `.env`, который исключён из репозитория
и из образа; в командной строке планировщика его писать не следует — она видна
в списке задач.

При заданном ключе формы загрузки на странице `/ui/etl` не выводятся: страница не может
передать ключ, не раскрыв его каждому, кто её открыл. В этом режиме данные принимаются
программным интерфейсом с заголовком `X-API-Key` или регламентным заданием обмена,
которое читает ключ из окружения. Ручная загрузка через браузер остаётся способом
локальной демонстрации, то есть режима без ключа.

## Что не входит в решение

Ролевая модель на несколько групп пользователей, единый вход организации, шины обмена,
кластеризация и автоматическое масштабирование не входят в текущую реализацию.
Архитектурные решения описаны в записях [`docs/adr/`](adr/). Реализован один общий ключ
на изменяющие операции; веб-интерфейс им не закрывается и в промышленном контуре выносится
за обратный прокси с внешней аутентификацией. Эндпоинты записи защищены от чтения
произвольных файлов и ограничены по размеру входных данных, но контур в целом рассчитан
на доверенную сеть.
