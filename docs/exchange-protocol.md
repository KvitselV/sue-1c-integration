# Протокол обмена данными

Механизм интеграции — **файловый обмен по версионированному контракту**. Причина
выбора и рассмотренные альтернативы: [ADR 0001](adr/0001-file-exchange-instead-of-live-1c.md).

Контракт: `schemas/1c_retail_exchange.schema.json` (JSON Schema 2020-12), версия **2.0**.

---

## Структура пакета

```json
{
  "meta": {
    "contractVersion": "2.0",
    "exchangeId": "EX-ACCOUNTING-018",
    "sourceSystem": "1C:Retail",
    "configuration": "1С:Розница 3.0 (контракт файлового обмена)",
    "exportedAt": "2026-05-26T10:00:00Z",
    "currency": "RUB",
    "periodFrom": "2026-05-01",
    "periodTo": "2026-05-31"
  },
  "stores": [ { "ref": "store-01", "code": "TT-01", "name": "ТТ Центральная", "city": "Казань", "format": "супермаркет", "isActive": true } ],
  "products": [ { "ref": "nomen-01", "sku": "MLK-1L", "name": "Молоко 3,2% 1 л", "category": "Молочная продукция", "unit": "шт" } ],
  "saleDocuments": [
    {
      "ref": "accounting-doc-000525",
      "number": "ОРП-000525",
      "date": "2026-05-01",
      "storeRef": "store-01",
      "documentType": "sale",
      "lines": [
        {
          "ref": "accounting-line-0001864",
          "productRef": "nomen-01",
          "quantity": 358.0,
          "amount": 31862.0,
          "costAmount": 22733.28
        }
      ]
    }
  ]
}
```

Фрагмент взят из `data/fixtures/accounting/exchange_accounting_018.json`.

Каждый пакет самодостаточен: он содержит и справочники, и документы. Это позволяет
загружать пакеты в любом порядке и повторно, не согласовывая состояние справочников.

### Обязательные и необязательные поля

| Блок | Обязательно | Необязательно |
|------|-------------|---------------|
| `meta` | `contractVersion`, `exchangeId`, `sourceSystem`, `exportedAt`, `configuration` | `currency`, `periodFrom`, `periodTo`, `comment` |
| `stores[]` | `ref`, `code`, `name` | `city`, `format`, `isActive` |
| `products[]` | `ref`, `sku`, `name`, `category` | `unit` |
| `saleDocuments[]` | `ref`, `number`, `date`, `storeRef`, `lines` | `documentType`, `currency` |
| `lines[]` | `ref`, `productRef`, `quantity`, `amount` | `discountAmount`, `costAmount` |

Лишние поля запрещены (`additionalProperties: false`) во всех объектах: незамеченная
опечатка в имени поля привела бы к молчаливой потере данных.

## Версионирование контракта

`meta.contractVersion` проверяется первым. Приёмник принимает только версии из
`SUPPORTED_CONTRACT_VERSIONS` (сейчас — `2.0`); пакет с другой версией отклоняется
целиком с понятной ошибкой, а не разбирается «как получится».

Совместимое изменение (новое необязательное поле) версию не меняет. Несовместимое
(новое обязательное поле, изменение смысла существующего, удаление) требует новой
версии, обновления `SUPPORTED_CONTRACT_VERSIONS` и записи в этом документе.

## Способы передачи

| Способ | Когда применяется | Ограничения |
|--------|-------------------|-------------|
| `POST /api/etl/upload` (multipart) | штатный приём выгрузки | размер — `SUE_MAX_UPLOAD_BYTES` (32 МБ), документов — `SUE_MAX_BATCH_DOCUMENTS` |
| `POST /api/etl/import` (имя файла или каталога) | демонстрация регламентного обмена | только внутри `SUE_FIXTURES_DIR`; отключается `SUE_ALLOW_LOCAL_PATH_IMPORT=false` |
| `POST /api/etl/pull` | приём с эмулятора выгрузки 1С (`/hs/exchange`) | только хосты из `SUE_EMULATOR_ALLOWED_HOSTS`; это не живая ИБ, см. [`emulator.md`](emulator.md) |
| `python scripts/seed.py` | первичное наполнение | тот же конвейер, без обходных путей |

Абсолютные пути и переходы вверх по каталогам отклоняются с кодом `unsafe_path`.

Проверочный прогон (`dry_run=true`) валидирует пакет и считает итоги, ничего не
сохраняя, — им имеет смысл предварять реальную загрузку новой выгрузки.

## Этапы обработки на стороне СУЭ

| № | Этап | Что происходит | При ошибке |
|---|------|----------------|-----------|
| 1 | Чтение | контроль размера, декодирование UTF-8, разбор JSON, вычисление SHA-256 | прогон `failed`, `stage=load`, данные не изменяются |
| 2 | Создание записи прогона | `etl_runs` со статусом `started`, хеш и `exchangeId` | — |
| 3 | Проверка структуры | JSON Schema целиком | ошибки в `etl_errors`, `stage=validate_schema` |
| 4 | Проверка правил | версия контракта, ссылочная целостность, знаки, точность, дубли, границы периода | ошибки в `etl_errors`, `stage=validate_rules` |
| 5 | Загрузка | upsert справочников, вставка документов и строк порциями | откат транзакции, прогон `failed` |
| 6 | Завершение прогона | статус, счётчики, длительность, сообщение | — |

### Правила приёмника (этап 4)

Приёмка идёт по принципу «всё или ничего»: **любое** нарушение уровня «ошибка»
отклоняет пакет целиком (`failed`), данные не изменяются, а все нарушения попадают
в `etl_errors`. Частичная загрузка означала бы, что итоги приёмника заведомо не сойдутся
с итогами источника, — то есть обессмысливала бы сверку. В таблице ниже указано, какая
именно запись называется в журнале как причина отклонения.

| Правило | Уровень | Запись в журнале |
|---------|---------|------------------|
| `meta.contractVersion` поддерживается | ошибка | `meta/contractVersion` (схема) |
| `storeRef` есть в `stores` пакета | ошибка | документ и путь `saleDocuments/N/storeRef` |
| `productRef` есть в `products` пакета | ошибка | строка и путь `…/lines/N/productRef` |
| `amount` и `quantity` строго положительны | ошибка | строка (схема) |
| `quantity = 0` при `amount ≠ 0` | ошибка | строка |
| Точность: `amount` ≤ 2 знаков, `quantity` ≤ 3 знаков | ошибка | строка и значение |
| `ref` уникален внутри пакета (документы и строки) | ошибка | запись с повторяющимся `ref` |
| `date` в пределах `periodFrom`…`periodTo`, если они заданы | ошибка | документ и дата |
| `documentType` из `sale`, `return` | ошибка | документ (схема) |
| `costAmount` более чем втрое превышает `amount` | предупреждение | пакет принят, замечание в журнале |

Точность проверяется арифметикой `Decimal`, а не ключевым словом `multipleOf`:
последнее выполняется над числами с плавающей точкой и даёт ложные срабатывания.

### Статусы прогона

| Статус | Значение |
|--------|----------|
| `started` | прогон начат; у завершённой загрузки такого статуса не бывает |
| `success` | всё принято, ошибок нет |
| `partial` | часть документов отклонена на этапе записи, остальные загружены; штатная валидация до этого этапа не допускает (пакет обязан быть самодостаточным), поэтому статус относится к защитной проверке загрузчика |
| `failed` | пакет не принят, данные не изменялись |

## Идемпотентность

Ключ идемпотентности — `source_ref` (GUID ссылки объекта 1С). Повторная передача
того же пакета обновляет записи и не создаёт дублей, поэтому повтор обмена после
обрыва связи безопасен и не требует ручной сверки.

Строки документа перед вставкой удаляются и по идентификатору документа, и по
`source_ref` строки: строка могла быть перенесена между документами в новой выгрузке,
и без второго условия появился бы дубль.

Изменённые значения в повторной выгрузке применяются — это обновление, а не вторая
запись. Полнота обеих гарантий проверяется тестами загрузки.

## Сверка после загрузки

```bash
curl "http://localhost:8000/api/reconciliation?path=accounting"
```

Сравниваются числа документов и строк, выручка, количество и учётная себестоимость.
Расхождение считается в минимальных единицах (копейках и тысячных долях), поэтому
`matched: true` означает совпадение до копейки. Контрольные суммы, посчитанные
генератором, записаны в `manifest.json` и проверяются независимо от загрузки.

## Регламент обмена

| Параметр | Значение в реализации |
|----------|----------------------|
| Периодичность | по факту передачи пакета; выгрузка на стороне источника не автоматизирована |
| Гранулярность пакета | календарный месяц (сценарии генератора разбивают историю по месяцам) |
| Порядок загрузки | произвольный: пакеты самодостаточны |
| Повторная загрузка | безопасна, идемпотентна |
| Аудит | `etl_runs` и `etl_errors`, страница `/ui/etl` |
| Разбор сбоев | [`operations.md`](operations.md) |

## Расширение до онлайн-обмена

Интерфейс `OneCSource` отделяет источник от конвейера. Класс `ODataSource` объявлен
и **сознательно не реализован**: его метод выбрасывает `NotImplementedError`
с объяснением причины. При появлении доступа к информационной базе достаточно
реализовать один метод `iter_batches`; валидация, загрузка, расчёт показателей
и интерфейс остаются без изменений.
