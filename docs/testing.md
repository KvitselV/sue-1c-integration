# Тесты

## Как запускать

```powershell
.\tasks.ps1 test          # весь набор на SQLite
.\tasks.ps1 test-core     # покрытие ядра с порогом 85%
.\tasks.ps1 coverage      # HTML-отчёт в htmlcov\index.html
.\tasks.ps1 test-pg       # прогон ядра на PostgreSQL
```

```bash
make test
make test-core
make coverage
make test-pg              # нужен SUE_TEST_PG_URL
```

Отдельные срезы:

```bash
pytest tests/unit                     # быстрые проверки без БД и HTTP
pytest tests/api -k security          # только проверки безопасности API
pytest -m pg -p no:randomly           # PostgreSQL, без перестановки порядка
pytest -k "не" --collect-only         # посмотреть, что будет запущено
```

## Структура

```
tests/
  conftest.py                      настройка окружения, генерация данных, фикстуры
  factories.py                     сборка минимальных пакетов обмена
  unit/          (133 тестов)      арифметика, валидация, конфигурация, KPI, витрина, эмулятор, PDF
  integration/   (57 тестов)       ETL, сверка, регламентный обмен, миграции, генератор, PostgreSQL
  api/           (65 тестов)       контракт, ошибки, пагинация, витрина, контроль доступа, PDF
  ui/            (46 тестов)       рендеринг страниц и локальные ресурсы
```

Всего 301 тест. Из них 4 помечены `pg` и пропускаются без `SUE_TEST_PG_URL`
(тест соединения проверяет, что база действительно PostgreSQL, — иначе маркер
создавал бы ложное впечатление о проверке).

## Принципы

**Тесты не изменяют рабочую копию.** `conftest.py` создаёт временный каталог на сессию,
генерирует туда небольшой набор данных и указывает на него `SUE_FIXTURES_DIR`
и `SUE_DATABASE_URL`. Каталог `data/fixtures` в репозитории не читается и не
перезаписывается; после прогона временный каталог удаляется.

**Изоляция на уровне теста.** Фикстура `db` перед каждым тестом очищает все таблицы
и сбрасывает кэш долей себестоимости. Порядок тестов перемешивается
`pytest-randomly`, поэтому скрытая зависимость от порядка проявляется сразу.

**Данные для проверки чисел собираются фабриками.** Там, где нужен точный ожидаемый
результат, пакет собирается из `tests/factories.py` на нескольких строках с заданными
суммами, а ожидание считается вручную. Сгенерированный набор используется только там,
где важен объём и разнообразие.

**Предупреждения — это ошибки.** В `pyproject.toml` включено `filterwarnings = error`,
поэтому устаревшие вызовы (например, `datetime.utcnow()`) ломают сборку, а не тонут
в выводе. Исключение сделано только для предупреждений внутри SQLAlchemy.

**Три уровня фикстур данных:** `db` — пустая база; `loaded_db` — база с загруженным
основным сценарием; `client` и `empty_client` — HTTP-клиент над заполненной и пустой
базой соответственно (пустая нужна, чтобы страницы отдавали «нет данных», а не 500).

## Что закрыто проверками

### Контракт обмена (`unit/test_validator.py`, 25)

Валидный пакет даёт ноль замечаний. По одному тесту на каждое правило: неизвестная
ссылка на магазин или номенклатуру, отрицательные и нулевые суммы, `quantity = 0`
при `amount > 0`, дублирующийся `ref`, лишнее поле (`additionalProperties: false`),
неверный формат даты, отсутствующий `meta`, неподдерживаемая версия контракта,
пустой массив документов, точность сверх двух знаков в сумме и трёх в количестве,
себестоимость, втрое превышающая сумму (предупреждение, а не отказ).

### Арифметика денег (`unit/test_money.py`, 20)

Округление до копейки по правилу «половина вверх», отсутствие потери точности при
переводе рубли ↔ копейки, отказ на нечисловых значениях и на `inf`/`nan`, поведение
на границах (`0.005`, отрицательные суммы), доля в процентах при нулевом знаменателе.

### Конфигурация и безопасность путей (`unit/test_paths_and_config.py`, 19)

Выход за каталог фикстур отклоняется во всех формах: `..` в начале и в середине пути,
абсолютный путь Windows и POSIX, сетевой путь UNC. Некорректная конфигурация
(неподдерживаемая СУБД, ставка накладных или доля себестоимости вне диапазона) приводит
к отказу при создании настроек, а не к неверным расчётам. Относительные пути
приводятся к абсолютным. Отдельно зафиксировано, что порог предупреждения выше целевого
отклоняется (иначе оценка рентабельности теряет смысл), что барьер доступа по умолчанию
выключен и что защита чтения без заданного ключа не запускается — иначе сервис оказался бы
недоступен целиком.

### Рентабельность (`unit/test_profitability.py`, 13)

Ручной расчёт на наборе из нескольких строк совпадает до копейки. Проверяется
происхождение: выручка — `accounting`, накладные — `modeled`, производные — `derived`;
точка со полной себестоимостью даёт `accounting`, без себестоимости — `modeled`,
смешанная — `accounting+modeled` с долями, дающими в сумме 100%. Фильтр по периоду
действительно сужает выборку; агрегация в СУБД равна сумме по строкам; рост доли
накладных монотонно снижает операционную рентабельность; отсутствие данных даёт
`None`, а не исключение.

### Витрина и сравнение периодов (`unit/test_mart.py`, 13)

Строка витрины действительно плоская (ни одного вложенного объекта) и соответствует
объявленной модели ответа; перечень колонок выгрузки покрывает все поля строки, поэтому
добавленный показатель не потеряется в CSV; происхождение себестоимости в плоской форме
сохраняется. Светофор: значение, равное порогу, относится к лучшей оценке, отрицательная
рентабельность — к «ниже нормы». Сравнение периодов: абсолютное и относительное изменение
считаются от базового периода; изменение рентабельности выражено в процентных пунктах;
при нулевой базе относительное изменение равно «не определено», а не нулю или бесконечности;
точка, отсутствующая в одном из периодов, остаётся в выдаче с признаком неполноты.
Периоды по умолчанию отсчитываются от последней даты в данных, а не от текущей.

### Русские подписи (`unit/test_i18n.py`, 28)

Проверяется не перевод как таковой, а полнота словарей: каждый статус прогона, тип
документа, этап загрузки и источник происхождения имеют русскую подпись. Незакрытое
значение утекло бы в интерфейс латиницей. Отдельно
зафиксировано, что подписи статуса прогона (`сбой`) и уровня записи журнала (`ошибка`)
не совпадают, а пустое значение отображается как «—», а не «None».

### ETL (`integration/test_etl.py`, 18)

Точность раздельных счётчиков; повторная загрузка того же пакета не меняет ни
количество строк, ни суммы; инкрементальный пакет добавляет только новое;
изменённая сумма в повторной выгрузке обновляет строку, а не создаёт дубль;
невалидный пакет даёт статус `failed`, записи в `etl_errors` и **неизменные** данные;
исключение внутри загрузки помечает существующий прогон как `failed` — «зависших»
`started` не остаётся; каталог без JSON даёт понятный отказ; проверочный прогон
(`dry_run`) считает итоги и ничего не сохраняет; возвраты уменьшают выручку.

### Сверка (`integration/test_reconciliation.py`, 7)

На каждом сценарии расхождение равно нулю по всем позициям. Отдельно проверяется,
что неполная загрузка **видна** в отчёте: если тест не может обнаружить расхождение,
он ничего не доказывает.

### Регламентный обмен (`integration/test_exchange_job.py`, 9)

Успешный прогон загружает пакеты и подтверждает совпадение контрольных сумм; проверочный
режим ничего не сохраняет и сверку не выполняет (сверять нечего — приёмник не менялся);
отклонённый пакет даёт код возврата «сбой», недопустимый или несуществующий путь —
код «обмен не начался», причём база при этом остаётся пустой. Проверяется и то, что отчёт
не содержит абсолютных путей файловой системы и читается как текст, а не как
escape-последовательности. Отдельно прогоняется сама команда, которую ставят
в планировщик: код возврата и сохранённый файл отчёта.

### Миграции (`integration/test_migrations.py`, 3)

`alembic upgrade head` создаёт схему, `downgrade base` её снимает, а сравнение
схемы из миграций со схемой из моделей не выявляет различий — забытая ревизия
ломает сборку.

### PostgreSQL (`integration/test_postgres.py`, 4)

Ядро прогоняется на настоящем PostgreSQL: ETL, сверка, идемпотентность и — главное —
показатели одного и того же пакета на PostgreSQL и SQLite сравниваются между собой
и должны совпадать. Это и есть доказательство переносимости целочисленного хранения
денег.

### Генератор данных (`integration/test_datagen.py`, 15)

Один `--seed` даёт побайтово одинаковый результат, разные — различающийся;
сгенерированный пакет проходит валидацию контракта; `manifest.json` совпадает
с фактическим содержимым; каждый краевой сценарий после загрузки даёт ожидаемый
статус; все 16 некорректных примеров действительно нарушают правила и покрывают
заявленный перечень.

Отдельная группа тестов проверяет правдоподобие данных, а не только их формальную
корректность: количество штучных товаров целое, весовых — кратно шагу весов, сумма
равна количеству × цена − скидка (то есть выведена из количества, а не наоборот),
скидки действительно появляются при заданной доле, а часть недель остаётся без
продаж. Без этих проверок генератор мог бы выдавать «33.7 упаковки сыра».

### API (`api/test_api.py`, 34)

Схема OpenAPI содержит типизированные модели, а не пустые объекты; `404` для
несуществующей точки в рентабельности; `422` при `date_from > date_to`
с кодом `invalid_period` и при лишнем поле в теле запроса; пагинация `limit`/`offset`;
единый формат ошибки на всех путях; каждый показатель в ответе имеет источник
и пояснение методики; CSV отдаётся в UTF-8 с BOM; `X-Request-Id` возвращается клиенту.
Безопасность: пять вариантов выхода за каталог фикстур → `400` `unsafe_path`;
файл больше предела → `413`; пустой файл → `400`; отключённый локальный импорт → `403`.
Отдельно проверяется, что при недоступной БД `/api/health/ready` отдаёт `503`
и `status: degraded`, а `/api/health/live` продолжает отвечать `200`, и что отчёт
сверки не раскрывает абсолютный путь файловой системы сервера.

### Витрина и сравнение в API (`api/test_mart_api.py`, 7)

Витрина отдаёт плоские строки с оценкой рентабельности и происхождением себестоимости;
CSV начинается с BOM и разбирается с разделителем «;» без потери колонок; фильтр периода
действительно сужает суммы. Отдельный тест закрывает ловушку маршрутизации: путь сравнения
объявлен до пути с идентификатором точки, иначе слово `compare` попадало бы в параметр-число
и запрос отклонялся бы как некорректный. Перевёрнутый период даёт `422` с указанием, какой
из двух периодов задан неверно.

### Контроль доступа (`api/test_security.py`, 13)

При заданном ключе загрузка файлом и по пути без заголовка `X-API-Key` даёт `401`
с кодом `unauthorized`, с корректным ключом — `201`; неверный ключ любой длины отклоняется,
а не вызывает ошибку сравнения. Проверено, что по умолчанию закрыта только запись, а режим
`SUE_PROTECT_READ` закрывает и чтение, при этом пробы живости и готовности вместе с версией
остаются открытыми: иначе оркестратор счёл бы исправный сервис недоступным.

### Интерфейс (`ui/test_pages.py`, 47)

Все страницы отдают `200` и содержат ключевые русские подписи (`учёт`, `модель`,
`расчёт`); в разметке нет ссылок на внешние ресурсы; нет невыведенных значений вида
`None`/`Undefined`; несуществующая точка показывает страницу ошибки; выбор периода
действительно меняет содержимое; на пустой базе страницы отдают `200` с сообщением
«нет данных»; все статические файлы, включая локальный
`/static/vendor/chart.umd.min.js`, доступны — это и есть проверка работы без интернета.
Страница сравнения проверяется отдельно: без параметров она подставляет два соседних окна
по данным, заданные периоды сохраняет в форме, а на пустой базе объясняет, что нужно
выполнить загрузку. Оценка рентабельности («норма», «внимание», «ниже нормы») присутствует
в таблице показателей. Отдельно проверено поведение страницы загрузок при включённом
барьере доступа: формы приёма данных не выводятся, ключ в разметку не попадает,
а способ загрузки указан текстом — страница не предлагает действие, которое сама
выполнить не может.

## Покрытие

| Область | Покрытие | Порог в CI |
|---------|----------|-----------|
| Ядро (`domain`, `etl`, `adapter_1c`, `money`) | 94% | 85% |
| Проект целиком | 94% | 70% |

Порог проверяется отдельной стадией `coverage:core` — снижение покрытия останавливает
сборку. Непокрытыми осознанно остаются: заглушка `ODataSource` (не реализована по
условиям работы), ветки настройки журналирования и обработчики отказа СУБД, которые
воспроизводятся только на недоступной базе.

Покрытие здесь — не самоцель, а индикатор: строка, ни разу не выполненная в тестах,
не проверена ничем. Содержательная гарантия — в матрице выше и в сверке контрольных
сумм, дающей ровно ноль расхождения.

## В CI

`.gitlab-ci.yml` выполняет: `lint` (ruff, ruff-format, mypy, `alembic check`) →
`test` (SQLite и PostgreSQL параллельно) → `coverage` (пороги) → `build` (образ) →
`smoke` (поднять контейнер, применить миграции, загрузить данные и дёрнуть
`/api/health/ready`, `/api/profitability`, `/api/reconciliation`). Отчёт JUnit
и покрытие в формате Cobertura публикуются как артефакты merge request.
