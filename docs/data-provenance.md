# Происхождение данных

Документ отвечает на два вопроса: откуда взялись сами данные и откуда взялся каждый
показатель, посчитанный по ним. Это разные вещи, и смешивать их нельзя.

---

## 1. Данные: синтетические, воспроизводимые, документированные

> **Все данные в проекте синтетические.** Они структурно совместимы с контрактом
> обмена 1С:Розница и правдоподобны по порядку величин, но **не являются выгрузкой
> реальной информационной базы** и не позволяют делать выводы о каком-либо предприятии.
> Причина отсутствия реальных данных зафиксирована в
> [ADR 0001](adr/0001-file-exchange-instead-of-live-1c.md).

Данные создаёт пакет `sue.datagen`:

```bash
python -m sue.datagen --out data/fixtures            # сценарии по умолчанию
python -m sue.datagen --out data/fixtures --list     # перечень сценариев
```

Генерация детерминирована: один `--seed` даёт побайтово одинаковые файлы; это
проверяется тестом, а не декларируется. Рядом с данными пишется `manifest.json`
с параметрами, контрольными суммами, хешами файлов и той же оговоркой о синтетике.

### Сценарии

| Сценарий | Точки | История | Себестоимость | Возвраты | Что проверяет |
|----------|-------|---------|---------------|----------|----------------|
| `accounting` | 6 | 8–77 недель | 80% строк | 3% | основной демонстрационный набор |
| `no_cost` | 2 | 40 недель | нет вовсе | нет | показатель помечается как смоделированный |
| `short_history` | 1 | 8 недель | все строки | нет | расчёт на коротком периоде новой точки |
| `returns_heavy` | 1 | 52 недели | 90% строк | 15% | выручка считается за вычетом возвратов |
| `large` | 6 | 156 недель | 70% строк | 4% | производительность: 26 тыс. документов, 130 тыс. строк |
| `invalid/` | — | — | — | — | 16 пакетов с одним нарушением каждый |

### Как формируются значения

| Величина | Правило | Обоснование |
|----------|---------|-------------|
| Недельная выручка точки | базовый уровень × сезонность × внутримесячная волна × тренд × шум | воспроизводит форму реального ряда: годовая сезонность (амплитуда 5–14% по точкам), рост или спад (−0.15…+0.90% в неделю), случайный разброс 5–11% |
| Количество в строке | **сначала количество**: целое для штучных товаров, кратное 50 г для весовых | обратный порядок (количество = сумма ÷ цена) даёт значения вида «33.7 упаковки сыра» |
| Сумма в строке | количество × цена − скидка | сумма следствие количества, а не наоборот |
| Скидка | в 25% документов, 5–15% от суммы | розница без скидок нереалистична; скидка передаётся полем `discountAmount` и уже вычтена из `amount` |
| Себестоимость | сумма × доля категории × разброс ±3% | доли по категориям заданы в `data/fixtures/modeled/cost_markup_by_category.json` |
| Наличие `costAmount` | с вероятностью `cost_coverage` | воспроизводит неполноту учётной выгрузки |
| Документы | 5–9 в неделю на точку (24–32 в объёмном наборе) | «Отчёт о розничных продажах» по кассовой смене; несколько касс дают несколько документов в день |
| Возвраты | доля недель по `return_rate`, сумма 1–30% недельной | методика учитывает возвраты, значит они должны быть в данных |
| Недели без продаж | 2–3% недель в `accounting` и `large` | закрытая точка: идеальных данных не бывает, разрыв в ряду должен обрабатываться |

### Каталог

| Что | Значения |
|-----|----------|
| Торговые точки | 6: два супермаркета, три «у дома», один киоск; Казань, Набережные Челны, Альметьевск |
| Недельная выручка точки | 145–420 тыс. руб. — порядок величин продуктовой розницы соответствующего формата |

Значения каталога подобраны так, чтобы результаты расчётов были интерпретируемыми.
Это делает их правдоподобными, но не делает реальными.

## 2. Показатели: метка источника у каждого значения

Каждое значение, попадающее в интерфейс, API или выгрузку CSV, снабжено меткой
происхождения и пояснением методики. Показатель без источника создать нельзя:
тип `ProvenanceValue` отвергает неизвестную метку
([ADR 0004](adr/0004-explicit-data-provenance.md)).

| Метка | В интерфейсе | Что означает |
|-------|--------------|--------------|
| `accounting` | учёт | значение пришло из выгрузки |
| `modeled` | модель | значение получено по заданному параметру |
| `derived` | расчёт | значение получено из показателей выше |
| `accounting+modeled` | учёт+модель | смешанный случай, доли выводятся отдельно |

### Распределение по показателям

| Показатель | Источник | Пояснение |
|------------|----------|-----------|
| Выручка, возвраты, количество | `accounting` | сумма `amount` и `quantity` из контракта |
| Себестоимость строки с `costAmount` | `accounting` | поле контракта |
| Себестоимость строки без `costAmount` | `modeled` | сумма × доля себестоимости категории |
| Себестоимость точки | `accounting`, `modeled` или `accounting+modeled` | зависит от полноты выгрузки; доли `cost_accounting_share_pct` и `cost_modeled_share_pct` в сумме дают 100% |
| Накладные расходы | `modeled` | выручка × `SUE_OVERHEAD_RATE` (по умолчанию 12%) |
| Валовая прибыль и маржа | `derived` | выручка − себестоимость |
| Операционная прибыль и маржа | `derived` | валовая прибыль − накладные расходы |

### Моделируемые параметры вынесены в файлы

| Файл | Содержание |
|------|-----------|
| `data/fixtures/modeled/overhead_params.json` | доля накладных расходов и диапазон анализа чувствительности |
| `data/fixtures/modeled/cost_markup_by_category.json` | доли себестоимости по категориям и область применения |

Параметры не «зашиты» в код: их можно заменить согласованными с предприятием
значениями, не меняя расчёт. Влияние моделируемой ставки накладных на итог измеримо
через параметр `sensitivity_delta` эндпоинта рентабельности.

## 3. Что из этого следует для выводов

Допустимо утверждать: механизм интеграции переносит данные без потерь (сверка даёт
ровно ноль расхождения), методика расчёта рентабельности воспроизводима, доля
моделируемых величин измерена и показана.

Недопустимо утверждать: конкретные значения рентабельности торговых точек, выводы
о сезонности продуктовой розницы, оценки эффективности реального предприятия.
Для таких утверждений нужна выгрузка из действующей информационной базы.
